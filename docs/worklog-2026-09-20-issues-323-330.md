# Review of issues #323 and #326–330

The requested scope is local investigation and repair of confirmed CoS defects. The six open
reports were read with their available comments on 2026-09-20. None had comments or attached
diagnostic logs at review time. Automatic compaction interrupting an unfinished task remains
intended behavior; continuation and ownership must still work correctly.

The shared working tree already contained extension compatibility, final-capture, queue and
browser-recovery changes. Those changes were inspected and preserved. This review adds two
repairs, described below, without installing, committing, publishing or changing GitHub issues.

## Tunnel repair

`src/main/tunnel/index.ts` previously tested each entire raw log line against a regex containing
bare `401`, `403` and `invalid_request_error`, before parsing JSON or filtering harmless events.
For example, a normal `poll failed; backing off` event with `retry_in_ms: 401` permanently stopped
the child and reported a rejected key. A local MCP 401 or a general HTTP 400 had the same effect.

The pinned upstream source was inspected at `openai/tunnel-client` tag `v0.0.14`:

- `pkg/controlplane/internal/poller.go` publishes `retry_in_ms` independently of the actual
  `status_code`, alongside the `poll failed; backing off` message.
- `pkg/controlplane/fx/fxmodule.go` emits `tunnel metadata fetch failed` with structured status.
- `pkg/controlplane/internal/tunnel_service_client.go` formats legacy transport errors with
  the `controlplane client` / `controlplane responder` owner and actual response status.

The repair checks the known failed operation and structured status/error after parsing and
severity filtering. A numeric HTTP status takes precedence over words in the error text.
Legacy text requires transport ownership and an authorization error. Genuine rejections still
stop exactly one process and do not retry indefinitely; network retries retain their existing
owner. The access diagnostic names account/organization/key/tunnel configuration without
claiming that every 401 is an invalid API key.

`test/tunnel-lifecycle.test.ts` adds seven non-authentication cases and five real rejection
cases, checking child termination, restart count, health ownership and repeated log delivery.
The first six negative cases failed against the unchanged code, then passed after repair.

## Handoff repair

`src/main/session/handoff.ts` appended `session(action="read", ...)` when a plan existed even
though the Core declarations no longer contain that tool. The old test explicitly required
the plan details to be absent, preserving the broken instruction.

The handoff now includes its session's saved explanation, step names, statuses and details,
clearly identified as reported progress rather than verified completion. The handoff owner
performs the existing middle-omission policy after reserving this exact plan and the exact
continuation marker. `continuation.ts` supplies its token. `bridge.ts` no longer independently
estimates a notice or trims the same content with a separate budget.

The model's original brief is still validated independently: a large plan cannot make a tiny
incomplete handoff acceptable. Existing stored handoffs are not rewritten. The single saved
handoff remains the source for retries, browser delivery and provenance matching.

`test/agent-plan.test.ts` covers the actual plan, absent/cleared plans, rejection of a stub,
multilingual maximum-size plan content and preservation of both ends of an oversized brief.
`test/resume.test.ts` exercises capture and command redemption through the actual bridge,
store and continuation pipeline, proving that plan text and the exact marker fit the 96,000
character message limit. Provider execution is simulated by that integration fixture.

## Open

- **Goal reply obligation does not move on handover.** `moveGoalObjective`/`moveGoalSwitch`
  run on commit; the pending row in `goalReplies` for chat A stays keyed to A and is forgotten
  once A is superseded. The comment in `bridge.ts::inspectOwedGoals` ("the obligation travels
  to the replacement with everything else") is wrong. Effect: one lost nudge; the loop resumes
  after B's first answer. Either move the row or fix the comment.
- **Goal/Loop prompts have no rule for permission questions.** Nothing tells the meta-prompter
  what to do when ChatGPT asks to do something irreversible or outside the stated work (delete,
  force-push, pay, send). Loop example 2 teaches "decide it in one line and push on", which can
  green-light a destructive step. Suggested: one sentence per prompt and trailer, answer only
  what the requirements already decide, refuse or defer anything irreversible the user never
  asked for. Changing a default means moving the current text into the superseded list so
  untouched installs migrate.
- **After a handover the register-mimicry copies the brief.** In chat B the "user" messages
  are the app-typed brief, so "write in the person's own register" copies its formal tone.
- **Terminal continuation retention is measured from `openedAt`.** `sweep()` drops committed
  and aborted records `2 × CONTINUATION_TTL_MS` after opening, so a days-old automatic ticket
  that aborts is forgotten immediately and a replayed ack starts a fresh transaction instead
  of getting "already done". Measure from the settle time.
- **Legacy state files.** 64 `request-correlation-recency-*.json`, `session-cursors.json`,
  `goal-drafts.json` (Aug 30) in the state directory are unreferenced by any code and the
  durable store does not scan the directory. Safe to delete; not deleted.
- **Log observations without a code finding.** `EXEC_RESULTS_UNREAD`, "Invalid session read
  cursor", `write_stdin` exit 1 with empty output, and the model guessing a `/totec/...` root
  are correct refusals or instruction drift, not app bugs. Phantom `turn_start`/`turn_end`
  flapping (worker-12: 235 turns for 8 request ids) is addressed by the content-script
  `openedUserMessageId` guard that was already in the tree.
- **Static reads only, not exercised here:** Linux/macOS Chrome discovery, POSIX process-group
  kills, tunnel packaging per platform, extension discovery and retry alarm, session listing
  (cached, paged, O(page)). No defects found by reading.

## Second run, 2026-09-02 12:27–13:31 (three workers, compaction window 50 k)

Prime session `2026-09-02-59d89ec6`, four chats, three automatic compactions at 12:38, 12:50 and
13:01 that all landed within ten seconds. The run then degraded from 13:17, and the user's report
("nothing arrived until I brought Chrome forward and clicked through the tabs") reconstructs to

| 13:29:39 | Replacement chat `6a980897`: 0 user messages, 0 assistant messages, 6 tool calls, `AGENTS_BUSY`; ticket armed, never acked | The user's Escape emptied the composer between `destinationDispatch` and the click; `send()` returned false, the resume path returned without a word, `continuationJournalPending` stayed up | Page proves nothing was sent → `/compact destinationLost` → `releaseContinuationDestinationSendNow()` (dispatch and claim back), old command retired, fresh resume queued at once; gate released |

Not bugs: the 12:45:50 "Connection interrupted" on all three workers at once was network-wide and
the app reloaded all three within two seconds; the 12:50 "Message delivery timed out" turns
ended `failed` while the models kept calling tools, which request-id attribution carried without
loss; the `WORKER_IDENTITY_LOST` pair at 13:30–13:31 was one request id retried by ChatGPT from a
page that produced no evidence, after the user had started blocking chats. The reload handout
itself was not late: every repair the app queued was carried out by the extension's next
30-second alarm pass (26 s and 17 s at 13:28:00).

# Bug audit — 2026-08-31

Three-worker adversarial audit of the current Chat On Steroids / ChatGPT Local Files tree on
`rebuild/2.0.3-from-2.0.2` at `2c6967a18e7f48244e8528316b879ca395f01fa4`.

This pass was deliberately broader than the open-GitHub-issues remediation plan. It looked for
new correctness bugs, hidden scaling costs, duplicated authorities and algorithms whose stated
contract is stronger than their implementation. Discovery was split across core architecture,
browser/runtime, and tools/release. Prime then relayed one common shortlist back to all three
workers. A finding is listed below only if **all three workers independently re-read the current
code and agreed on both the defect and the fix direction**, and Prime independently traced the
same boundary.

No source, test, config or AppData file was changed during discovery/cross-review. The only change
from this audit is this document.

## Unanimously confirmed findings and agreed fixes

### 1. Proven request ownership is documented as permanent but can still be evicted — HIGH correctness

**Where:** `src/main/session/correlation.ts`, `test/correlation.test.ts`, MCP caller-attribution paths.

The correlation module states the core ownership invariant explicitly: once an exact page request id
has been joined to an MCP request, that owner is permanent because the same workflow may keep issuing
calls after its page reloads or closes (`correlation.ts:11-24`). The implementation contradicts that
contract: `MAX_CORRELATIONS = 50_000`, and `trim()` deletes the oldest owner when the map crosses that
count (`correlation.ts:40,69-75`). `requestCorrelation()` has no durable cold-miss lookup; after
eviction it simply returns null (`270-299`).

This is a follow-up hole in the August 25 LRU fix. That fix correctly refreshed insertion order when
an old live owner was observed again, but the regression test now explicitly accepts losing a
non-refreshed owner at entry 50,001 (`test/correlation.test.ts:138-167`). A workflow does not become
safe to disown merely because 50,000 unrelated ids arrived after its last page observation.

**Agreed best fix:** make eviction follow semantic lifetime, not map size. The authoritative request-id
owner must live at least as long as the retained session/workflow that proves it. If RAM still needs a
bound, make the in-memory map a cache and add an exact durable request-id lookup for cold misses; do
not let cache eviction mean "ownership unknown". Delete the current arbitrary authority-loss behavior.

**Regression:** prove an exact owner still resolves after more than 50,000 newer ids even when its
page is gone and it was not recently refreshed. Separately prove that removing the owning retained
session is the lifecycle boundary that may remove its request-id facts.

### 2. `listAllSessions()` is capped before sorting but is used by correctness/recovery callers — HIGH correctness

**Where:** `src/main/session/store.ts`, `src/main/session/recorder.ts`,
`src/main/session/correlation.ts`, `src/main/mcp/session-tool.ts`.

`store.ts:1523-1529` explicitly calls the API a **bounded legacy/model-facing list** and says not to use
it for correctness properties that promise to see every retained session. `readAllSummaries()` stops
after 5,000 directory entries **before** it sorts by `updatedAt` (`1530-1551`), and `listAllSessions()`
exports that view (`1650-1652`). The same store already has the correct primitives: an uncapped process
catalog (`readEverySummary()`) and ordered keyset pagination (`listSessionPage()`).

Three current consumers nevertheless treat the capped universe as authoritative:

- correlation crash-window reconciliation starts with `listAllSessions()` and only then takes the
  newest 100 (`correlation.ts:190-225`), so it can miss a globally newer session that happened to lie
  beyond the arbitrary `readdir()` prefix;
- deterministic Unattributed repair loops over `listAllSessions()` even though the function promises
  to repair every exact request-id fact it can prove (`recorder.ts:810-854`);
- model-facing session search pages the capped array and can emit `search_complete: true` at its end
  (`session-tool.ts:227-287`) while retained sessions still exist.

The store already has >5,000-session regressions proving that correctness operations must use the
uncapped catalog (`test/session.test.ts:268+`). These callers bypass that lesson.

**Agreed best fix:** delete or rename the ambiguous `listAllSessions()` compatibility API so callers
cannot accidentally read "All" as authoritative. Correlation restore should ask the ordered catalog
for its bounded newest crash window; session search should page the catalog directly so its own
100-session scan budget is the only bound; attribution repair should iterate/query the uncapped
catalog for Unattributed sessions. Do not raise 5,000 to a larger magic number.

**Regressions:** construct 5,001+ summaries with the relevant target deliberately outside the first
directory prefix and prove (1) request-correlation restore sees the true newest crash-window proof,
(2) attribution repair reaches the deep Unattributed bucket, and (3) session search cannot report
complete until all retained pages are reachable.

### 3. Older-session pagination can accept a stale page after a hot first-page refresh — HIGH correctness

**Where:** `src/renderer/chat.ts`, `test/session-list-refresh.test.ts`.

`loadSessions()` owns a generation fence (`chat.ts:311-339`): every newest-page refresh increments
`sessionsLoadGeneration` and stale first-page responses are rejected. `loadMoreSessions()` mutates the
same `sessions` + `sessionPageCursor` state but does not participate in that authority (`341-357`). It
captures a cursor, awaits IPC, then unconditionally merges the old page and overwrites the current
cursor.

Deterministic interleaving:

1. Retained sessions are S1..S65; newest page is S1..S60 with cursor C60.
2. Scrolling starts `loadMore(C60)`.
3. New session N arrives; the hot refresh becomes N,S1..S59 with cursor C59.
4. The old C60 request returns S61..S65 with `nextCursor = null`.
5. The renderer merges those rows and replaces C59 with null. S60 is now missing and the UI has no
   cursor left that can ever retrieve it.

The existing 65-session regression (`test/session-list-refresh.test.ts:207-270`) is sequential, so the
tree stays green while this overlap remains possible. This is a regression at the exact pagination
boundary introduced to fix the prior 60-row hard cap.

**Agreed best fix:** make both loaders obey the same list-generation authority. Before the await,
`loadMoreSessions()` captures `{generation: sessionsLoadGeneration, cursor}`. After the reply it may
commit only if the generation is unchanged **and** `sessionPageCursor` still equals the captured
cursor; otherwise discard the stale page. Do not add retry timers—the next scroll/hot refresh already
uses the current cursor.

**Regression:** defer the C60 response, commit a newer C59 first-page refresh, then resolve C60 and
prove it is discarded; the next page must recover S60 and eventually expose all 66 unique rows. Also
cover the inverse ordering where the older page legitimately commits before the hot refresh.

### 4. Recursive Codex walk re-follows child symlink targets before skipping them — HIGH boundary + efficiency

**Where:** `src/main/codex/filesystem.ts`, `src/main/codex/read-backend.ts`, `test/read-backend.test.ts`.

`readDirectory()` deliberately keeps child symlinks opaque because following a child merely to
classify it can leak metadata/errors from outside an approved root (`filesystem.ts:266-283`). But its
`ReadDirectoryEntry` shape drops the symlink bit (`78-83`). `walk()` therefore calls `getMetadata()`
for every child (`387-394`); `getMetadata()` does `lstat` and then follows a link with `stat`
(`251-263`). Only after that target access does `walk()` skip a link when
`followDirectorySymlinks=false` (`395`).

The normal recursive read/glob caller passes `followDirectorySymlinks:false`
(`read-backend.ts:206-227`), so this both violates the stated opacity boundary and adds at least one
extra metadata syscall per ordinary entry, plus a second one for symlinks, across a walk that may
inspect tens of thousands of entries.

**Agreed best fix:** preserve `isSymlink` in `ReadDirectoryEntry`. In the normal `follow=false` path,
skip links directly and classify ordinary files/directories from the `Dirent` data already obtained by
`readdir({withFileTypes:true})`. Only stat/canonicalize a child when following directory symlinks is
explicitly requested or metadata is otherwise required. This removes the redundant N-stat path rather
than caching around it.

**Regressions:** place a directory symlink inside an approved tree whose outside target would throw or
be observable if statted; `walk(...followDirectorySymlinks:false)` must neither touch nor report that
target. Add a syscall-count regression proving a plain N-entry recursive walk does not call
`getMetadata()` N times merely to reclassify `Dirent`s.

### 5. MCP session cursors repeatedly materialize the whole journal — MEDIUM/HIGH algorithmic cost

**Where:** `src/main/mcp/session-tool.ts`, `src/main/session/store.ts`.

The model-facing session reader is cursor-shaped but not cursor-costed. Initial read, older-page read,
range continuation and update polling repeatedly call `readEvents()` for the whole session before
filtering/paging (`session-tool.ts:388-420,423-506`). On a cold/closed session `readEvents()` reads the
entire `events.jsonl`, splits/parses it, merges canonical messages, sorts and only then slices
(`store.ts:1016-1093`). Scrolling P pages through N events therefore trends toward O(P×N) journal
parsing; repeated update checks on a long dormant session pay O(N) even when nothing new exists.

The store already contains a bounded reverse reader for recent presentation tails
(`readRecentEvents():1095+`) and a sequence-cursor cache for recent live events. The missing piece is a
single store-level ranged journal primitive, not another MCP-specific cache.

**Agreed best fix:** give the session store one bounded/ranged reader that owns sequence high-water,
`from`/`before` limits, canonical-message merge and byte/event budgets. Build `readRecentEvents()` and
MCP latest/older/update cursors on that same authority and delete the "full read then filter" cursor
paths. Start with streaming/ranged reads; add sparse seq→byte checkpoints only if measurement proves
they are necessary.

**Regressions/measurement:** instrument journal bytes/lines parsed while paging a large closed session.
Cost per page/update must stay proportional to the requested window (plus a bounded seek budget), not
the complete history. Preserve cursor chronology and canonical-message semantics.

### 6. Swarm persistence debounces disk I/O after eagerly building the whole snapshot — MEDIUM efficiency/structure

**Where:** `src/main/agents.ts`, `src/main/index.ts`, `src/main/durable.ts`.

`agents.changed()` invokes the persistence callback on every critical or telemetry mutation
(`agents.ts:415-421`). Production wires that callback as
`writeDurableSoon(SWARM_STATE, snapshotSwarm())` (`index.ts:278-283`). `writeDurableSoon()` correctly
coalesces disk writes for 300 ms, but the expensive value has already been built before it gets the
chance to coalesce.

`snapshotSwarm()` copies every dormant owner history (`agents.ts:3608-3627`), while `serializeAgents()`
clones/filter-scans every agent queue and staged-finish view (`3631-3677`). Dormant histories are
retained until explicit history clearing, so a tiny context-token/telemetry change can become O(total
retained worker history) synchronous CPU many times inside one 300 ms window even though only one
disk write survives.

**Agreed best fix:** debounce/dirty-mark **before snapshot materialization**. The persistence adapter
should schedule one lazy snapshot producer per debounce window, then serialize current state once when
the write actually drains. Keep the existing immediate critical barrier as the explicit eager path;
do not create a second snapshot model. Shard dormant histories only if measurement after this deletion
still justifies it.

**Regression/benchmark:** restore hundreds/thousands of dormant histories, fire a burst of telemetry
mutations and count `snapshotSwarm()`/serialization executions. The ordinary debounced lane should
materialize once per write window while immediate critical writes remain exact.

### 7. Exact dormant conversation ownership is repeatedly discovered with full-history scans — MEDIUM algorithm/structure

**Where:** `src/main/agents.ts`, MCP identity/worker-fence callers.

`dormantRunForWorkerConversation()` and `dormantAgentForConversation()` scan every dormant run and its
agents on each lookup (`agents.ts:607-640`). The latter is used at many lifecycle and identity
boundaries (`~1693,1760,1836,2655,2970,3160,3307,3392`), including paths reached from ordinary MCP
dispatches. Yet `restoreSwarm()` already validates global conversation uniqueness before admitting
restored owners; normal bind/park/move paths likewise know exactly which conversation they mutate.

That means hot lookups repeatedly recompute a uniqueness property that should already be part of the
owner model. With retained dormant histories, exact ownership lookup grows linearly with unrelated old
runs.

**Agreed best fix:** make conversation→owner addressing part of the authoritative broker state. Rebuild
it once while validating restore, then update it atomically at bind, park/reactivate, continuation move,
worker finish/clear and history clear. Route both active and dormant ownership queries through that one
registry and delete the duplicate dormant walkers. Treat duplicate insertion as corruption/fail-closed
at the mutation boundary, not something every read rediscovers.

**Regression/measurement:** restore many dormant histories, resolve the last worker and an unrelated
conversation, and prove lookup work is constant-time with duplicate ownership rejected during restore
or mutation rather than silently chosen later.

### 8. Prime workspace still has two identities after conversation identity became authoritative — MEDIUM structural deletion

**Where:** `src/main/workspace.ts`, `src/main/mcp/kernel.ts`, `src/main/agents.ts`, workspace/agent tests.

`workspaceKey()` now states the intended rule clearly: exact ChatGPT conversation is the durable
identity; reusable `agent:*` keys are only bootstrap staging before a new worker reports its exact
conversation (`workspace.ts:62-75`). `currentWorkspace()` already migrates worker staging to the chat
key (`95-117`).

Prime still carries an older second-owner design: `primeWorkspace()` reconciles both
`chat:<prime-conversation>` and `agent:prime`, mirrors the winner back to both (`157-186`), and
`releasePrimeWorkspace()` copies `agent:prime` back to the chat key at run end (`188-207`). Current MCP
dispatch resolves exact request-id conversation evidence before identity-sensitive workspace use, and
`workspaceKey()` itself prefers that conversation whenever it exists. The remaining tests that
directly seed `agent:prime` preserve the old architecture rather than demonstrating a production
boundary that still needs it.

**Agreed best fix:** make Prime conversation-only. Keep `agent:worker-N` only as a temporary pre-bind
inheritance slot; delete the Prime mirror/reconciliation/release path and the tests/comments that
manufacture a null-conversation `agent:prime` workspace. If a real production call lacks exact Prime
conversation evidence, it should fail the same identity/workspace boundary as any other chat rather
than writing durable cwd under a reusable friendly id.

**Regressions:** first and later worker spawns inherit from `chat:<prime-conversation>`; Prime moving
projects during a swarm remains on the new project after the run parks; a later unrelated Prime cannot
inherit the previous run through `agent:prime`; a null-conversation call cannot create a Prime cwd.

### 9. `exec_command` discovery exceeds its budget on Windows PowerShell 5.1 — MEDIUM efficiency/portability

**Where:** `src/main/codex/tool-specs.ts`, `src/main/codex/shell.ts`,
`src/main/mcp/instructions.ts`, `test/mcp.test.ts`.

The missed verifier failure was exact, not timing noise:

```text
AssertionError: exec_command schema is 3572 bytes: expected 3572 to be less than 3500
test/mcp.test.ts:796
```

The test calls itself the **worst-case no-query discovery** budget, but the advertised schema is
currently host-shell dependent. `tool-specs.ts:21` computes `LAUNCHES_WINDOWS_POWERSHELL_5` from
`defaultUserShell()`, whose Windows resolution is PATH/PATHEXT-sensitive (`shell.ts:231-255`). When
PowerShell 7 (`pwsh`) is visible, `EXEC_COMMAND_CMD_DESCRIPTION` uses the 68-byte neutral text and the
full `exec_command` schema is 3455 bytes. When the same endpoint resolves Windows PowerShell 5.1, the
`cmd` property appends a 117-byte `&&`/`||` warning and the schema becomes 3572 bytes.

Prime reproduced both sides repeatedly: normal PATH with pwsh 7 available passed 3/3; a PATH restricted
to the same Node runtime plus Windows/System32/WindowsPowerShell 5.1 failed 3/3 at exactly 3572 bytes.
The original three audit workers had independently reproduced the same 3572-byte failure before this
follow-up (5/5, 3/3 and 1/1 isolated runs). Three fresh read-only reviewers then independently traced
the environment split and all classified it **REAL REGRESSION, not flaky benchmark**. The benchmark is
environment-sensitive/incomplete — pwsh 7 can false-green the stated worst-case contract — but the
oversized model-visible payload on a supported PS5-only Windows machine is real and deterministic.

History identifies the crossing precisely. Commit `7c37688` added the 117-byte PS5-only `cmd` suffix
and also added the same PS5 `&&`/`||` guidance to Core server instructions. Commit `5463f17` later added
97 bytes of important polling guidance to `EXEC_COMMAND_DESCRIPTION`; that moved the PS5 variant from
about 3475 to 3572 while pwsh 7 moved from about 3358 to 3455. The 3500 budget did not move. Removing
the polling contract would merely bring PS5 back to ~3475 with only 25 bytes of headroom and would
leave discovery shape dependent on PATH.

**Agreed best fix:** delete the PS5-only suffix/conditional from `EXEC_COMMAND_CMD_DESCRIPTION` and
keep the existing shell-version-neutral 68-byte text (`Shell command to execute. To read a file, use
the read tool instead.`). Keep the conditional PS5 `&&`/`||` warning once in Core server instructions
(`mcp/instructions.ts:79-84`), where all three reviewers confirmed the model still receives it. Preserve
`5463f17`'s polling obligation; do **not** raise or conditionalize the 3500-byte budget, pin CI to one
PATH, or create separate PS5/pwsh budgets. This is a deletion/deduplication fix and makes both Windows
shell environments advertise the same ~3455-byte exec schema.

**Regressions:** keep the existing `< 3500` per-tool budget unchanged; assert the `exec_command.cmd`
description is shell-version-neutral / does not contain `Windows PowerShell 5.1`; keep a server-
instructions assertion that PS5 guidance is present when PS5 is the resolved default. The size test
should no longer need PATH mutation or module-reset tricks because environment-specific shell grammar
has one owner: server instructions, not the discovery schema.

## Already tracked / deliberately not duplicated as new findings

The audit independently rediscovered several important problems that already have stronger treatment
in `docs/open-issues-remediation-plan-2026-08-31.md`; they are evidence for that plan, not new items:

- Compact & Resume currently has overlapping continuation-WAL and broker `PrimeTransfer`/TTL/freeze
  authority. Keep the remediation-plan decision that the continuation transaction must be sole durable
  A→B authority and delete the duplicate broker transfer lifecycle.
- Legacy resume-shadow repair still has hot-path callers such as `/activity`; keep the plan's bounded
  startup compatibility-repair design rather than documenting another fallback.
- Public-history privacy verification can false-green in shallow/no-tag Actions and does not prove
  deleted ancestor blobs clean. S6.1 of the remediation plan already specifies full-history/tag
  completeness and unique reachable-blob scanning.

### Release-plan concretization: Windows NSIS artifact

All three workers also confirmed one **validation gap**, but agreed not to call it a tenth architecture
bug without an artifact-level failure: Windows release jobs smoke `win-*-unpacked`, while the shipped
`Chat-On-Steroids-Setup-*.exe` itself is not installed/launched/uninstalled. The remediation plan
already requires testing the exact release candidate / installed build, so its Windows DoD should say
explicitly: silently install each matrix Setup EXE into an isolated per-user/temp location, run the
existing packaged-runtime readiness smoke against the installed root, launch the installed app, then
silently uninstall and verify the installed executable is removed. Reuse the existing smoke instead
of adding another validator.

## Investigated but not accepted in this consensus pass

These were intentionally left out because the three-worker final review did not establish the same
confidence/priority:

- removing the 1-second `content.js` observe/paint safety tick entirely — plausible efficiency gain,
  but needs live evidence that MutationObservers cover every site remount/theme/control case;
- per-name durable write queues instead of the current global serialization chain — plausible
  head-of-line improvement, but needs measurement and crash-order proof before adding queue machinery;
- treating every raw tunnel log `401/403` as a false-terminal bug — the regex is broad and runs before
  structured parsing, but an actual client diagnostic showing a non-credential 401/403 is still
  needed before changing terminal auth semantics;
- streaming the JavaScript no-ripgrep content-search fallback instead of collecting candidates first —
  valid low-priority algorithmic improvement, but below the nine agreed changes and not worth
  broadening this pass before the common invariants above are fixed.

## Recommended implementation order

1. **Identity/history correctness:** findings 1 and 2 together. They share the principle that an
   explicitly proven durable fact must not disappear behind a cache/list bound.
2. **Renderer omission race:** finding 3. Small, isolated generation/cursor fix with deterministic
   regression.
3. **Filesystem boundary + syscall deletion:** finding 4. Preserve symlink opacity and delete redundant
   metadata work in one change.
4. **MCP discovery deduplication:** finding 9. Delete the PS5-only duplicate from the `exec_command`
   schema, keep the warning once in server instructions and keep the existing hard byte budget.
5. **Session journal algorithm:** finding 5. Introduce one ranged store primitive and delete MCP
   full-read cursor paths.
6. **Broker scaling:** findings 6 and 7. First debounce before materialization; then make exact
   conversation ownership an authoritative address rather than repeated scans.
7. **Workspace cleanup:** finding 8 after lifecycle regressions prove exact Prime conversation identity
   at every workspace-mutating production boundary.

Each batch should prefer net deletion or consolidation. Do not solve these findings with larger caps,
new retry timers, secondary heuristic indexes or another state machine.

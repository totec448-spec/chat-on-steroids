# Bug audit — 2026-08-23

> Historical note (2026-08-24): the `session action=history/status` behavior documented below
> was replaced by the single `session` tool's `search/read` contract. The observed identity-wait
> failure remains incident evidence; the current session reader no longer performs caller lookup.

Everything found by reading the existing code while building the goal loop, and what was done
about it. Ordered by what it costs when it happens, not by where it lives.

Each entry says what the code did, why that was wrong, and what now holds it. Where a defect
was seen in the wild rather than reasoned about, the observation is quoted.

---

## 1. A retired swarm's worker command could be adopted by the next run

**Where** `src/main/bridge.ts`

A worker bootstrap was identified by `worker:<agent>` — and `worker-1` is the name *every*
run gives its first worker. The command journal is durable, so a command left over from run A
(a crash, a restart, a teardown that raced an in-flight open) matched run B's `worker-1`
exactly. Run B then adopted A's command: A's task text, A's command id, A's lease.

Nothing downstream could notice. A worker chat is bound by the command it redeemed, so the
binding was internally consistent and simply pointed at the wrong swarm.

**Now** `CommandSpec` for a worker carries the broker's `runId`. It is part of the dedupe key,
so two runs' `worker-1` are two commands. A command whose run is no longer current is retired
rather than left to match. `requestWorkerChat` refuses to queue at all when there is no current
run, because a worker bootstrap outside a run has no safe meaning. The journal is version 3;
v1/v2 worker rows are dropped on restore rather than migrated, since there is no fact on disk
that says which run owned them — the restored broker re-requests anything it is genuinely owed.

## 2. Lost-ACK worker recovery trusted a label the page chose

**Where** `src/main/bridge.ts` (`/events`), `extension/background.js`, `extension/content.js`

Normal worker binding happens on the exact command ACK. `/events` is the recovery path for a
lost ACK, and it bound a conversation to whatever agent name the page reported. That name is
`worker-1`. Any page that said `worker-1` while some `worker-1` command was still leased could
take the binding.

**Now** the page must also present the exact random command id it redeemed, and the pair is
only honoured against a still-leased command of the *current* run. The extension carries
`agentCommandId` alongside `agent` through the offline queue and the flush. An extension build
old enough not to send it loses recovery, which is the safe half of that trade.

## 3. The offline queue merged gap markers from different worker chats

**Where** `extension/content.js`

When the queue overflows, the dropped entries are collapsed into one `chat_error` gap marker,
keyed by `conversationId + agent`. Two documents opened for the same friendly worker id — the
same reuse as above — shared a key and collapsed into one record covering both.

**Now** the command id is part of the key, so the marker describes exactly one chat.

## 4. `session` told a model its history did not exist

**Where** `src/main/mcp/tools-core.ts`

Observed on 2026-08-23: `session action=history` waited fifteen seconds for this app to place
the call in a conversation, failed to, and answered

> No recorded session is available.

The recording it was talking about was hundreds of events long. It simply could not be reached
from a call whose `x-request-id` was never resolved inside the evidence window. The sentence is
not merely unhelpful, it is false, and it is a dead end: a model that reads "no session"
concludes there is no history and rebuilds the work from the filesystem, which is what happened.

**Now** an unresolved caller is told what actually happened and handed the recordings — id,
time, event count, title — with the instruction to call again with `session_id`. `session_id`
was already an ordinary argument of this tool, so listing the ids exposes nothing that asking
for one did not. The same list is offered by `action=status` when no chat can be resolved, and
appended when a history search matches nothing, since a search that finds nothing in *this*
recording is often a search aimed at the wrong one — a compacted chat's work lives in the
session it inherited, under an id the caller has no reason to know.

## 5. `exec_command` could hand a recycled process id to the previous owner

**Where** `src/main/mcp/tools-core.ts`

Process ids are small and reusable, and chat ownership lives in a registry separate from the
Codex process manager. A process that exited could be evicted by the manager without ever
passing through `write_stdin`, leaving its owner row behind. The next allocation could return
that same numeric id — and until `noteExecOwner` published the new owner, the *old* chat was
still authorised to write to and interrupt the new chat's process.

**Now** the stale owner row is cleared at the allocation boundary, before the child is inserted
into the manager. Nobody owns a brand-new id until the call that minted it returns.

## 6. A desktop click could land on a screen nobody had looked at

**Where** `src/main/computer/index.ts`, `src/main/mcp/tools-desktop.ts`, `src/main/mcp/instructions.ts`

`frameId` was described as "strongly recommended". Omitting it meant the coordinates were
applied to whatever the latest global frame happened to be — and the frame is global to the
app, so another chat or another agent can replace it between the screenshot a caller looked at
and the click it sends. A missing id turned an attribution failure into a real mouse action on
unrelated pixels, silently.

**Now** a coordinate action without `frameId` is refused with `FRAME_REQUIRED`. Semantic refs
resolve the real control at action time and never use image coordinates, so they stay exempt.
The tool description and the server instructions say "required" instead of "recommended".

## 7. The goal loop would never stop waiting for a composer in use

**Where** `extension/content.js`

`insertPrompt` refuses a composer that already holds text, so a draft aimed at one somebody is
typing in is kept and retried. `GOAL_TYPING_WINDOW_MS` bounds that patience at two minutes,
after which the message is dropped rather than typed over a sentence in progress.

It could not expire. `goalTypingSince` marks when *this draft* first found the composer busy,
and it was cleared in the `finally` of every attempt — so every retry restarted the window and
`Date.now() - goalTypingSince` was always zero. The draft would have retried for as long as the
user kept a half-written message in the box.

**Now** it is cleared only once the draft is spent. A draft still waiting keeps its start time.
Covered by *waits for a composer somebody is using, then gives up rather than typing over them*.

## 8. One unknown reasoning level would have wiped every root and permission

**Where** `src/main/config.ts`

`goal.reasoning` is a `z.enum`. A rejection inside it fails the whole `configSchema.parse`,
which sends the file through `conservativeRecoveryConfig()` — every root dropped, every tool
permission revoked, read-only forced on.

The set of levels is a provider's vocabulary, not this app's. A config written by a build that
knows one more level than the one reading it is a case this app will meet, and it is not worth
a settings file for one word in one field.

**Now** the enum falls back to `default` instead of rejecting, exactly as the blank model id is
repaired rather than refused.

## Checked and found already sound

Two of the reported symptoms turned out to be the class already closed in **v1.9.6**
(`5137393`), and are recorded here so the next reader does not go looking again.

**An empty compaction was sent — the resume prefix with nothing after it.** That is the shape
of a brief that was captured before ChatGPT finished writing it. It is now refused at three
independent layers: `settleBrief` will not deliver until four signals agree and keep agreeing
for fifteen seconds; `deliverBrief` refuses an empty or interrupted capture outright and says
so on the page; and `briefShortfall` refuses a brief too short to have carried the session it
claims to summarise, both at the bridge route (where the refusal can be worded for the user)
and inside `createHandoff`, which is the one function that writes a handoff to disk. A refused
compaction leaves the session exactly where it was.

**The prime role did not move to the replacement chat.** The transfer machinery is intact:
`commitPrimeTransfer` moves `run.primeConversationId` and the prime agent's binding as part of
the session rebind commit, guarded by a freeze that pins the handover across the commit, and
`repairPrimeConversationAfterRecovery` repairs the projection when a crash lands between the
durable session commit and the in-memory move. Queued worker reports survive it untouched:
they live on the prime *agent*, keyed by `PRIME_ID`, not on its conversation.

What was actually broken in the observed run was upstream of all of that — the commit lost a
302 ms race to the recorder, which invents a session for any conversation it has not seen, so
the rebind found its destination already owned and refused. Fixed in v1.9.6 by the expected-
chat window that makes the recorder wait rather than invent.

**Automatic compaction triggers.** The rule is level-triggered (`autoCompactionReady`: over the
line, trigger not yet spent) and combined at the point of use with `chatIsWorking`, which is a
fact about the live browser connection rather than the recording. That is what fires it while
the model is working — the only moment a handoff is worth writing — while leaving a stale 500k
chat alone when it is merely opened. The one trigger is consumed durably before ChatGPT is
touched, so a failed attempt cannot replay itself; the manual button is always still there.
